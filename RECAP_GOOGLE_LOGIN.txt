RÉCAP : CONNEXION AVEC GOOGLE (Sign in with Google)
Projet CampusMarketplace
Généré le : mercredi 05 août 2026

Ce document explique TOUTES les étapes qu'on a suivies pour faire fonctionner
le bouton "Continuer avec Google", du début à la fin, avec le rôle de chaque
pièce dans le système.

--------------------------------------------------------------------------------
1. POURQUOI C'EST COMPLIQUÉ ? (les bases)
--------------------------------------------------------------------------------
"Se connecter avec Google" repose sur un protocole appelé OAuth 2.0 / OpenID
Connect (OIDC). L'idée :

   - Ce n'est PAS notre application qui vérifie le mot de passe Google.
   - C'est GOOGLE qui vérifie que l'utilisateur est bien qui il dit être.
   - Google nous remet ensuite un "certificat d'identité" (un jeton signé)
     que notre backend contrôle avant de créer la session.

En clair : l'utilisateur tape son mot de passe sur la page de Google,
jamais chez nous. C'est pour ça qu'on ne voit jamais de champ mot de passe.

--------------------------------------------------------------------------------
2. ÉTAPE 0 : PRÉPARATION DANS LA CONSOLE GOOGLE CLOUD (config manuelle)
--------------------------------------------------------------------------------
On a dû créer une "application OAuth" dans le Google Cloud Console pour que
Google sache QUELLES applications peuvent utiliser son service de connexion.

Actions faites :
   1. Créer un projet Google Cloud.
   2. Activer l'écran de consentement OAuth (mode "External").
   3. Ajouter des "utilisateurs de test" (nos adresses email en mode test).
   4. Créer une "OAuth Client ID" de type "Web application".
   5. Ajouter l'origine JavaScript autorisée : http://localhost:3000
      (l'URL de notre frontend).

Résultat obtenu : un CLIENT ID, qui ressemble à :
   636822661571-0o2jhgo266mg4al2bfb6qv05c53o42hd.apps.googleusercontent.com

Ce Client ID identifie notre application auprès de Google. Il est utilisé à
la fois par le frontend (pour afficher le bouton) et par le backend (pour
vérifier les jetons). C'est une clé PUBLIQUE : elle peut être visible, ce
n'est pas un secret.

--------------------------------------------------------------------------------
3. ÉTAPE 1 : CÔTÉ FRONTEND - AFFICHER LE BOUTON ET RÉCUPÉRER LE JETON
--------------------------------------------------------------------------------
Fichier principal : front/src/components/google-sign-in-button.tsx

Ce composant fait 3 choses :

   1. Il charge le script officiel de Google appelé "GIS"
      (Google Identity Services) :
          https://accounts.google.com/gsi/client
      C'est Google qui fournit ce script : il affiche le vrai bouton
      "Continuer avec Google" et gère la popup de connexion.

   2. Il configure le bouton avec notre CLIENT ID :
          window.google.accounts.id.initialize({
            client_id: "...notre client id...",
            callback: ...,
          })
      et
          window.google.accounts.id.renderButton(element, {...})

      => On donne notre Client ID à Google, et Google sait alors que le
         bouton est destiné à notre application.

   3. Quand l'utilisateur choisit un compte Google, le callback reçoit un
      objet contenant un "credential". Ce credential est un ID TOKEN :
      un jeton signé par Google qui dit "l'utilisateur machin@truc.fr a bien
      été authentifié par Google".

   4. Le frontend envoie ce jeton à notre backend :
          POST http://localhost:5000/api/auth/google
          body : { "credential": "....long jeton...." }

   5. Si le backend répond OK (avec user + token), on appelle login() du
      contexte d'authentification (comme pour un login email classique),
      on stocke le JWT, et on redirige vers la page d'accueil.

Page register (front/src/app/register/page.tsx) :
   - le bouton Google est affiché EN HAUT du formulaire,
   - le champ "pièce d'identité" a été retiré (on peut s'inscrire sans).

Elle pointe vers la fonction "googleLogin" du contrôleur.

--------------------------------------------------------------------------------
5. ÉTAPE 3 : CÔTÉ BACKEND - VÉRIFIER LE JETON (le point crucial)
--------------------------------------------------------------------------------
Fichier : back/src/controllers/auth.controller.ts -> fonction googleLogin

Pourquoi il faut vérifier le jeton ?
=> N'importe qui pourrait envoyer un faux "credential". Le backend doit
   PROUVER que le jeton vient vraiment de Google et qu'il est bien destiné
   à NOTRE application.

La vérification (faite par la bibliothèque google-auth-library) :

   1. Signature : Google signe chaque jeton avec sa clé privée. La
      bibliothèque vérifie la signature avec les clés publiques de Google.
      Si le jeton a été modifié ou fabriqué ailleurs, la signature ne
      correspond PAS => refus.

   2. Audience : le jeton doit être émis POUR notre application. La
      bibliothèque reçoit notre CLIENT ID en "audience" et vérifie que le
      jeton lui correspond. Comme ça, un jeton obtenu pour une AUTRE
      application ne fonctionne pas chez nous.

   Code équivalent :
      const ticket = await googleClient.verifyIdToken({
        idToken: credential,
        audience: process.env.GOOGLE_CLIENT_ID,
      });

      => Si ça échoue : réponse 401 "Token Google invalide".
      => Si ça marche : on récupère le payload qui contient l'email,
         le nom, et un identifiant unique ("sub") propre au compte Google.

--------------------------------------------------------------------------------
6. ÉTAPE 4 : CÔTÉ BACKEND - TROUVER OU CRÉER L'UTILISATEUR
--------------------------------------------------------------------------------
Toujours dans googleLogin. Après la vérification, 3 cas possibles :

   1. Un utilisateur a déjà ce "googleId" (déjà connecté via Google avant) :
      => on le retrouve et on le connecte directement.

   2. Aucun googleId, mais un compte existe avec ce MÊME email
      (inscrit avec email/mot de passe avant) :
      => on rattache le googleId à ce compte existant. Résultat : l'utilisateur
         peut se connecter ensuite avec Google OU avec son email/mot de passe,
         c'est le MÊME compte (pas de doublon).

   3. Aucun compte du tout (première fois) :
      => on crée le compte :
           - email        = l'email du payload Google
           - name         = le nom donné par Google
           - password     = NULL (pas de mot de passe chez nous !)
           - googleId     = l'identifiant unique de Google
           - role         = STUDENT
         (la pièce d'identité reste vide : l'upload est différé sur la page
          /carte-scolaire, obligatoire avant de publier une annonce)

Ensuite, le backend génère SON PROPRE jeton JWT (comme pour le login email)
et renvoie :
      { user: {...sans le password...}, token: "...." }

=> C'est ce JWT que le frontend stocke et utilise pour toutes les requêtes
   authentifiées (publier, messagerie, etc.).

8. LE PARCOURS COMPLET, DE A À Z (résumé visuel)
--------------------------------------------------------------------------------
   [Utilisateur]  clique "Continuer avec Google" sur notre site
        |
        v
   [Script GIS de Google]  ouvre la popup de connexion Google
        |
        v
   [Utilisateur]  tape son email/mot de passe (+ 2FA éventuelle) SUR GOOGLE
        |
        v
   [Google]  vérifie l'identité, puis renvoie à notre site un
             "ID TOKEN" (jeton signé, valable ~1h)
        |
        v
   [Notre frontend]  POST /api/auth/google avec le jeton
        |
        v
   [Notre backend]  1) vérifie la signature du jeton (vient de Google ?)
                    2) vérifie l'audience (destiné à notre app ?)
                    3) retrouve/crée/rattache l'utilisateur en base
                    4) génère SON propre JWT et le renvoie
        |
        v
   [Notre frontend]  stocke le JWT et connecte l'utilisateur
                    => il est connecté, sans jamais avoir tapé de
                       mot de passe chez nous

9. QUESTIONS FRÉQUENTES
--------------------------------------------------------------------------------
Q : L'utilisateur n'a pas de mot de passe, c'est sécurisé ?
R : Oui. C'est Google qui l'authentifie (avec son mot de passe + 2FA).
    Notre base ne contient aucun mot de passe Google (password = NULL),
    donc rien à voler. La sécurité repose sur la vérification du jeton
    (signature + audience) côté backend.

Q : Pourquoi il y a un CLIENT ID dans le frontend ET dans le backend ?
R : Le frontend s'en sert pour que Google affiche le bon bouton.
    Le backend s'en sert pour vérifier que le jeton reçu est bien destiné
    à notre application (audience). C'est une valeur publique, pas secrète.

Q : Que se passe-t-il si quelqu'un vole le jeton ?
R : Le jeton est court (expire ~1h) et lié à notre application (audience).
    Il ne peut pas être réutilisé par une autre app. En production, le site
    doit être en HTTPS pour que le jeton circule chiffré.

Q : Et si l'utilisateur avait déjà un compte email/password ?
R : Le backend relie son googleId à ce compte existant. Il peut ensuite se
    connecter des deux façons, c'est le même compte.

FIN DU RÉCAP GOOGLE
================================================================================
Dans la console Google Cloud. Voici le chemin exact :
1. Va sur https://console.cloud.google.com/apis/credentials/consent (connecté avec ton compte admin).
2. En haut à gauche, vérifie que ton projet est bien sélectionné.
3. Sur la page OAuth consent screen, descends jusqu'au bloc "Publishing status" → il affiche "Testing".
4. Clique sur le bouton "PUBLISH APP".
5. Google affiche une fenêtre de confirmation ("Your app will become available to any user with a Google Account") → clique "Confirm".
6. Le statut passe à "In production". C'est tout.
Deux précisions importantes :
- Aucune vérification Google n'est requise dans ton cas : on n'utilise que le "Sign in with Google" (identité : email + profil). La vérification (review) ne concerne que les applications qui demandent des accès sensibles (lire les emails, accéder aux fichiers Google, etc.). Ton app peut passer en production immédiatement.
- Après publication, la liste des "Test users" ne s'applique plus : n'importe quel compte Google pourra se connecter.
Pour que le bouton continue de marcher en ligne, pense aussi à ajouter ton URL de production dans APIs & Services → Credentials → ta "Web client" → Authorized JavaScript origins (et Authorized redirect URIs si besoin).
